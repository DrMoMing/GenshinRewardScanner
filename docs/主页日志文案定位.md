# 主页运行日志文案在哪里

主页日志由Python扫描服务与会话控制层生成，原生界面主要负责显示；与Harness无关。

## 文案与原始消息入口

| 文件 | 负责的内容 | 定位方式 |
| --- | --- | --- |
| [src/log_view.py](../src/log_view.py) | 将底层扫描诊断转成用户能读的消息，并筛掉耗时等技术输出 | `scan_message()`；例如“已识别第…件”“已到奖励行起点”“已到奖励行末尾，正在汇总”“内存余量不足…” |
| [src/app.py](../src/app.py) | 准备模型、截图恢复、表格连接与保存、任务开始结束等直接消息 | 搜索`self.hotkeys.log(`及`report_progress(` |
| [src/scanner_session.py](../src/scanner_session.py) | 原生版本的监听、取消、单卡排队、错误收尾与界面状态 | 搜索`status.set(`、`log(`；`log()`添加时分秒并进入界面日志队列 |
| [src/domain_run.py](../src/domain_run.py) | 页面扫描、拖动与端点等底层原始消息 | 搜索日志标签，或`write_held_probe()`、`initial_row_complete()` |

例如，想改“已识别第N件”的说法，先改`log_view.py`的最终返回文案；想改“表格已就绪…”或“识别池已预热…”，看`app.py`。`log_view.py`中用于匹配底层原文的前缀及正则是转换规则，和最终显示的文字是两个位置。

## 从生成到显示

1. `src/domain_run.py`及其他扫描模块输出任务诊断；`app.py`用`scan_message()`转换成适合界面的信息。部分服务消息在`app.py`直接生成。
2. `src/scanner_session.py`的`log()`接收这些消息，写任务日志、通知浮窗，再添加当前本地时间，排入主页日志队列。`drain_controls()`还接收后台学习等事件消息。
3. `src/session_state.py`的`LogState`保留界面所需的最近记录；`src/desktop_web_view.py`的`snapshot()`把记录放到`runtime.logs`中发给原生宿主。
4. `native/desktop_host/NativeDesktopHost.cs`的`ApplyLogs()`更新列表，设置最新一条、数量和颜色；`MainWindow.xaml`定义文字布局。它通常不生成扫描消息本身。

`src/scanner_gui.py`保留旧Tk界面的回调；当前原生版本在入口转入`scanner_session.py`，优先修改后者。

按用户后续反馈，已精简部分重复说明，具体改动如下。

## 用户指出的两条日志

它们的原始输出都在[src/domain_run.py](../src/domain_run.py)，此前只列转换和控制入口时漏了这个文件：

| 原始标签 | 生成函数 | 内容 |
| --- | --- | --- |
| `[端点试验]` | `write_held_probe()` | 拖动时新旧端点判据及耗时等诊断 |
| `[首帧完整性]` | `initial_row_complete()` | 首帧不能证明整排完整时，继续端点确认 |

新版首帧消息精简为“未确认横排可视边界；继续端点确认。”。`log_view.scan_message()`把正常端点消息转为“第N次拖动：外侧仍有卡片／外侧未见卡片／端点尚未确认。”；错误及未知格式仍保留原消息。

`app.py`中的生产读取循环先写完整原始行到扫描诊断文件，再进行消息转换。简短消息也会通过`scanner_session.log()`进入主页及任务记录，因此修改显示转换时，后续任务日志中的对应文本也会改变；已有日志原件不改写。

准备类消息也已按用户要求去掉重复的架构和“未操作游戏”等说明，保留当前状态、路数、失败原因、保存结果及操作提示。

运行日志另已精简表情、箭头、Markdown装饰及开发解释，保留失败原因、索引、坐标、耗时与必要文件位置。日志转换层同时兼容历史和新文案。结构化计时、控制协议以及OCR识别字符不属于装饰文案，不作替换。
